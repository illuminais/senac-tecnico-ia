UC08 Parte 1 — Conceitos

Q✔Por quêPor que a errada engana
1.1aUsuário do banco é uma conta com permissões, não uma pessoa. Uma pessoa pode ter várias contas, e uma conta pode ser usada por um sistema.(b) é a leitura do dia a dia: "usuário é quem usa". No banco, não.
1.2cMenor privilégio: só o necessário para a função, nada além.(b) confunde privilégio com hierarquia. Não é sobre confiança na pessoa, é sobre a tarefa.
1.3dSELECT é só leitura.(c) "dar permissão para outros" existe de verdade, mas exige WITH GRANT OPTION, que não foi dado aqui.
1.4bREVOKE tira privilégio.(c) DROP USER apaga a conta inteira. Resolve, mas é muito além do pedido: a pessoa continua trabalhando ali.
1.5cSQLite é um arquivo, sem servidor e sem contas. Quem controla o acesso é o sistema operacional.(a) "é a versão grátis" é o palpite natural de quem não sabe. Não existe versão paga do SQLite com DCL.
1.6dRestrito a quem precisa. É o menor privilégio aplicado a dado sensível.(b) "bloqueado para todo mundo" soa mais seguro, mas quebra o trabalho: alguém precisa emitir o contrato de adoção.

UC08 Parte 3 — A matriz

O que aceitar como certo: pequenas variações são válidas se a justificativa sustentar. Exemplos aceitáveis: veterinária com INSERT em animais (se ela também cadastra), estagiário sem acesso a adocoes (se o relatório dele for só sobre tempo de espera).

O que NÃO aceitar: qualquer acesso do estagiário ou da veterinária à tabela adotantes. Nenhum dos dois precisa de CPF para trabalhar. É o item que separa quem entendeu menor privilégio de quem só preencheu a tabela.

Coordenadora com ALL PRIVILEGES é aceitável, mas quem escreveu privilégio por privilégio, sem DELETE, mostrou mais cuidado, não menos. Vale A igual.

UC08 Parte 4 — Os comandos

CREATE USER 'veterinaria'@'localhost' IDENTIFIED BY 'senha123';
GRANT SELECT, UPDATE ON abrigo.animais TO 'veterinaria'@'localhost';
GRANT SELECT ON abrigo.adocoes TO 'veterinaria'@'localhost';

CREATE USER 'estagiario'@'localhost' IDENTIFIED BY 'senha123';
GRANT SELECT ON abrigo.animais TO 'estagiario'@'localhost';
GRANT SELECT ON abrigo.adocoes TO 'estagiario'@'localhost';

Erro de sintaxe pequeno (ponto e vírgula, aspas) entra no feedback escrito, não derruba a questão. O que derruba é dar privilégio que o perfil não deveria ter.

UC08 Parte 5 — Mudou o contexto

REVOKE SELECT ON abrigo.adocoes FROM 'estagiario'@'localhost';

b) Ele continua com SELECT em animais, o que faz sentido para quem cuida dos bichos no canil. Aceitar também quem tirou os dois acessos e justificou que ele não mexe mais com dados.

UC08 Parte 6 — Desafio

CREATE VIEW historico_sem_cpf AS
SELECT a.nome_animal, ad.data_adocao, p.nome
FROM adocoes ad
JOIN animais a   ON a.id = ad.id_animal
JOIN adotantes p ON p.id = ad.id_adotante;

GRANT SELECT ON abrigo.historico_sem_cpf TO 'veterinaria'@'localhost';

Aceitar qualquer resposta que diga "criar uma visão só com as colunas permitidas e dar acesso a ela em vez da tabela", mesmo sem a sintaxe completa. A ideia é o que conta.

UC06 Parte 1 — Conceitos

Q✔Por quêPor que a errada engana
1.1bProcesso tem memória própria. Threads dividem a memória do processo em que vivem.(a) associa thread com GPU. Thread é conceito de sistema operacional, existe na CPU também.
1.2cCada aba é um processo isolado. Por isso o estrago fica contido.(a) é a resposta de quem trocou os dois conceitos. Se fossem threads, uma travada derrubaria o navegador inteiro.
1.3aConcorrência é revezar. Paralelismo é acontecer junto de verdade, em núcleos diferentes.(b) inventa uma divisão CPU x RAM que não existe.
1.4bUma thread por vez executa bytecode Python dentro do processo.(a) é a armadilha: está quase certo. O Python consegue usar vários núcleos, com multiprocessing. O GIL limita threads, não o Python inteiro.
1.5dMilhares de núcleos simples fazendo a mesma conta em pedaços diferentes do dado.(a) "relógio mais rápido" é o oposto: o clock da GPU costuma ser menor que o da CPU. A vantagem é quantidade, não velocidade individual.

UC06 Parte 3 — Classificar

QRespostaJustificativa esperada
3.1GPUÉ a mesma conta repetida em muitos dados independentes.
3.2processos separadosSão programas diferentes, cada um com a própria memória. Um travar não pode derrubar o outro.
3.3threadsÉ o mesmo programa, dividindo a mesma memória, e o áudio fica esperando boa parte do tempo.
3.4GPUMesma operação aplicada a milhares de imagens ao mesmo tempo.
3.5processos separadosIsolamento: se um cair, o resto continua de pé.

A justificativa vale mais que a marcação. Quem marcou certo sem justificar, ou justificou com "porque é mais rápido", não evidenciou o indicador. Quem marcou errado mas justificou com a regra certa merece ser lido com atenção.

UC06 Parte 4 — O pipeline

OrdemEtapa
3milhares de núcleos da GPU fazem a mesma conta
4o resultado volta da VRAM para a RAM
2o lote é copiado da RAM para a VRAM
1o programa em Python separa as imagens em um lote

4.1 A CPU tem poucos núcleos, então ela reveza entre as imagens (concorrência). A GPU tem milhares, então ela faz de verdade ao mesmo tempo (paralelismo). Exigir as duas palavras usadas com sentido correto.

4.2 O lote precisa ser quebrado em lotes menores, que entram na VRAM um de cada vez. Aceitar também "usar uma GPU com mais VRAM" ou "diminuir o tamanho do batch".

UC06 Parte 5 — A máquina de verdade

Não há gabarito fixo: os números mudam de máquina para máquina. O que se avalia é a 5.3: o aluno precisa dizer que cada processo contém várias threads, então o total de threads é naturalmente maior. Quem inverteu não entendeu a relação.
